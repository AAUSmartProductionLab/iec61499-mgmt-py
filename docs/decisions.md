# Decisions

What was decided, in the order it happened. The plan itself is in
[next-steps.md](next-steps.md); what is built in [work.md](work.md).

| Decision | Answer |
| --- | --- |
| May ARSO be extended for building blocks and for what a skill's Contract, Step and Implementation contain? | Yes |
| Validator closed or open? | Closed, as the SHACL validation of the generation project is |
| Fill volume | A time at a fixed flow rate; the volume decides the time |
| Who executes plans | A multi-agent system: an agent per product and per resource, I4.0 bidding; resource agents use the skills, the AAS and the reconfiguration tools |
| Products | Prefilled syringe, cartridge or vial, as in the planner's examples |
| Planning | By hand in the planner's web UI for now; an automatic planner may write the same submodels later |
| Which skills need a capability? (7 Oct) | A composite skill does; a primitive is a building block and needs none; Occupy and Release are access control and need none |
| Where are a skill's parameters? (6 Oct) | With the skill: the inputs of its Operation. The Parameters submodel is optional and does not hold them |
| Capability element (6 Oct) | As IDTA 02020: the template's id, the meaning as a supplemental id |
| What does a step's binding hold? (7 Oct) | The smallest change: a parameter the skill hands down is a reference to that parameter of the skill (it was its name as a string); a constant stays a value. What a step runs with shows at the interface anyway; the planner's own bindings and the HMI are unchanged |
| Where do a contract's terms come from when there is no spec? (7 Oct) | From the AAS manifest the module's vendor provides: the descriptive half of step 1.2 is that manifest, not a file of our own |
| How is a product or a plan described? (7 Oct) | Like a module: an AAS type on the pydantic model (aas-model) and a profile that is its dump, built by the same tool. No description format of our own. Done for the product with its plan (`ProductTypeAAS`); the vial of the example line is such a profile |
| What does a module carry as its manifest? (7 Oct) | The pydantic dump (the profile). It is what `modreg profile` writes today, from the module spec (the YAML file a module's program is generated from) and the running program; storing it on the module is not built (step 1.3) |
| The planner reads its own skill catalog, the modules publish ARSO Skills. Which holds? (7 Oct) | The resource's skill definition. The web UI and the planner are adjusted to read it (step 2.2) |
| Is a plain wait (Dwell) kept, and is Dispense a skill of its own? (8 Oct) | Dwell is removed for now (its block types stay in the history); Dispense is offered like every other primitive |
| What has an AAS? (8 Oct) | The production system, each of its six modules (Loading, Filling, Stoppering, Capping, Inspection, Unloading) and every active component of a module: filling pump and linear axis; stoppering piston and linear axis; cap crimper and linear axis; top and side camera; Kuka robot and gripper (loading and unloading). The bill of material of the resources and the hierarchy of skills follow from these |
| What does a linear axis offer? (8 Oct) | The same two skills in every module: `MoveAxis(Position)` and `Home`. The axes are stepper motors with a limit switch, as on a 3D printer: the controller keeps the position itself (home at the switch, then the time it steps), and the direction follows from where the axis is and where it is to go. **Done 8 Oct** in the generator and in the filling and stoppering modules, run on FORTE with the simulator |
| Which way do capabilities and skills refer? (8 Oct) | One way: a capability names the skill that realizes it. A skill does not refer back |
| What is the stoppering module made of? (8 Oct) | As the others: a linear axis and one small linear actuator (the piston). **Done 8 Oct** |
| Is there a scale? (8 Oct) | Not physically. It is a part of the filling module with a simulated weight; it is tared when the module resets (**done**). The weight following what was dispensed is not built |
| How many robots? (8 Oct) | One Kuka for loading and one for unloading, each with a Raspberry Pi of its own. How 4diac controls them comes later (likely: start program 1, 2 or 3) |
| How is a component's AAS named? (8 Oct) | One per component as built in, with an id of its own (filling linear axis); what kind it is, is shared by all of that kind |
| How does a Raspberry Pi get its runtime? (8 Oct) | By one script, `runtime/install.sh`: Docker if missing, FORTE from the repository (`runtime/bin`), GPIO and PWM. **Done 8 Oct**, run on a Raspberry Pi 5 |
| Which Pi runs which module? (8 Oct) | The Raspberry Pi 5 (192.168.0.134) the filling module, the Raspberry Pi 4 (192.168.0.191) the stoppering module. The Pi 4 still has to be renamed and to get the new runtime |
| How are the axes driven and kept right? (8 Oct) | RepRap Stepper Motor Driver v2.3 (A3982): Step, Dir and an inverted Enable. An ordinary limit switch at the top goes straight to the Pi. The position is counted, so every operation ends by homing (**done 8 Oct**). Speed assumes an 8 mm screw and half steps until measured |
| Where do a skill's block type, instance and contract go? (8 Oct) | "Do what you need to make it work": block type, instance and hash are in the Control Configuration (Instances, each pointing at its skill or step); the contract stays with the primitive; what a primitive occupies is its component |
| How does a product's value reach a skill's parameter? (8 Oct) | No link from skill to capability. The parameter carries the meaning of the capability property it sets (a semantic id), as the product's parameter does; the plan's step binds the value |
| The Skills structure (7 and 8 Oct) | **Built 8 Oct as ARSO 0.7:** a skill is its commands (Start, Stop, Abort, Reset), each with its interface reference, an Operation named like it and its steps; the module's own commands are a submodel (Module); primitives are in the AAS of their component; the line, each module and each component is an AAS, told apart by its asset type. Published on the local AAS server |
| Are the agents part of the CIRP paper? (8 Oct) | No, or only as future work. The paper is the reconfiguration of a module from its AAS; the bidding system follows it |
| How does a vial move between the modules? (8 Oct) | On the ACOPOS 6D magnetic levitation table: shuttles carry it. They are controlled by Python code, not by IEC 61499, and need transport agents of their own |
| Where does a reconfiguration come from? (8 Oct) | The AAS is the desired state: a reconfiguration is a change to the module's AAS that the tools carry into the program. The scope is the changeover ("a good scoping for the reconfiguration"). The Skills submodel says what is wanted, the Control Configuration what was built. **Tried 8 Oct** (`modsync verify`, `reconfigure`) |
| Which stepper driver? (8 Oct) | A TB6600 (ordered) replaces the RepRap Stepper Motor Driver v2.3, which never energised the motor. Step, direction and enable as before, no change in the program |
| What does a command's list of steps look like? (9 Oct) | Like the planner's Production Sequence: the same elements (`Kind`, `Order`, `Branches`, `Condition`, ...) with the same semantic ids, so a skill is described and edited like a product's plan, with the module's components and their skills in place of materials. "The models have to keep evolving": ARSO, `modreg`, `modsync` and `modlink` change with it. **Built 9 Oct as ARSO 0.8**; the control still runs steps one after the other only |
| Fallbacks in a skill? (9 Oct) | Not now; maybe later |
| Where are the module's own commands? (9 Oct) | In the Skills submodel, as skills of a kind of their own: every skill element has the semantic id `.../skill`, and its kind (`Primitive`, `Composite`, `ModuleControl`) is a supplemental id. The Module submodel is gone. **Built 9 Oct** |
| How is a skill edited? (9 Oct) | By a plugin of the BaSyx web UI fork (`basyx-aas-web-ui`, branch `feat/process-sequence-pharma`) that opens on the Skills submodel, in the style of the product's sequence editor |
| What does the paper show? (9 Oct) | First that a skill can be edited and the change made in the program. If time allows, also a reconfiguration that follows from a product's steps, parameters and required capabilities |
| The Pi 4 (9 Oct) | Renamed `stoppering-module` and brought up to date on the user's request: system updates, the runtime by `runtime/install.sh`, the stoppering program |
| A module and the lab's resources (19 Oct) | Our modules are AAS resources in the PPR sense: a line, a module and a component are aas-model's `Resource`, with ARSO's Skills, Operational Data and Control Configuration added and the Control Component Instance and Variables left out. The registration service is `modreg serve` (aas-model has none); it also takes the plain `Resource` export of the lab's stations. Operational Data may become Time Series Data later. **Built 19 Oct** |
| Actions in the interface description (19 Oct) | aas-model's AID extension (`.../aid/ActionDefinition/1/0`, `synchronous`, `input`, `output`, `uav_componentOf` on the action), declared in ARSO. **Built 19 Oct** |
| ARSO's submodels in aas-model (19 Oct) | The templates and models of Skills, Control Configuration, Operational Data, Process Parameters and Production Sequence, and the types Module, Component, ProductionSystem and Product, go into aas-model so the full models are authored with it. On a local branch; how it reaches aas-model (fork and pull request, or access) is open |
| Which Pi is the filling module's? (20 Oct) | The Raspberry Pi 5 at 192.168.0.203; the Pi 5 at 192.168.0.134 was the wrong one |
| Which Pi is the stoppering module's? (22 Oct) | The Raspberry Pi 5 at 192.168.0.134 (user `admin`, renamed from filling-module to stoppering-module), no longer the Pi 4 at 192.168.0.191. The Pi 4 is no longer used (26 Oct) |
| How is the axis driven? (20 and 21 Oct) | A TB6600 at 4 microsteps and 2.8 A, its inputs straight on the Pi's pins (a level converter is not needed); a RATTMMOTOR stage with a 5 mm ball screw: 2 kHz, 12.5 mm/s. Home runs until the switch (60 s at most). A normally open limit switch between GPIO23 and GND |
| How does a block reach its pins? (21 Oct) | Still through the equipment item that owns them (one owner per pin: FORTE allows one observer per IO handle, a GPIO line one requester; several skills share an axis; the axis keeps its position), but each IO point has one address in FORTE's notation instead of a backend number, a Modbus ID and a handle name: `<Point>_Address` = `'LinearAxis_Step'`, `'modbus[...]'` or `'sim'`. **Built 21 Oct** |
| Who starts a module's program? (21 Oct) | The resource's own `START` block (an `E_RESTART` in every `EMB_RES`), wired in the resource to the head of the INIT chain, as 4diac programs usually are; the module's own `Boot` block is gone. The application is no longer complete without its resource's links, which matters only with several modules on one resource. **Built 21 Oct** |
| How is a generated program laid out? (21 Oct) | Compact, in the style the user arranged the filling module: blocks close together in their groups, groups side by side. A layout arranged in the IDE is kept; a block added since gets a free place below the others in its group. The resource view is left as the IDE builds it (it cannot be arranged in a file) |
| Where are a Pi's lines set up? (21 Oct) | In the IO block of each IO point, from its address (`gpio[...]`, `pwm[...]`): an equipment block needs no other block for its IO, and the same type runs on every target. Windows' FORTE gets stand-ins for GPIOChip and PWMChip (a FORTE patch). The separate line blocks are gone. **Built 21 Oct** |
| How are the skill blocks named and where is the release? (22 Oct) | Pins named for what they carry, with a comment each (e.g. `Session`, `Requested`, `Value`, `RUN`, `Holder`, `ReleaseAfter`); a module level skill's Control gives up all the skill holds at every end of a run on one module-wide release channel; the skill shows four groups: Core, Start, Sequences, Results. **Built 22 Oct** |
| What is old? (8 Oct) | Removed or archived on the user's go-ahead: the superseded plans and figures (`docs/archive`), the HMI interface documents, the installers of the tools on a Pi, `modsync`'s own AAS builder; the generator's test module `filler` is with the skill library's tests |
| Where does the HMI go? (26 Oct) | Into the BaSyx web UI fork (submodule `basyx-aas-web-ui/` since 26 Oct) as a module in Vue and TypeScript. A browser cannot speak OPC UA, so a small generic bridge in TypeScript (Node, node-opcua) stays on a server: it only calls, reads and subscribes the endpoints and nodes the interface description names, over WebSocket. Everything else (Skills, interface description, mappings) the module reads from the AAS itself. `modlink` stays in Python for scripts, the scenario runner and the agents; the HMI's own Python service and pages are retired after the port. **When:** after A4, B1 and B2. **The bridge is temporary**, for testing and work: the target is an HMI that commands a module through the elements of its Skills submodel and follows its state in the Operational Data submodel, where each state is a Property and also a reference to its series in a time-series database (such as InfluxDB) from which the history is read |
| Where do states, measurements and logs live? (26 Oct) | In Operational Data, as time series SMCs that follow IDTA's Time Series template (Metadata with its Record, Segments) but one series per SMC instead of one per submodel. Each series also has a `Latest` property for the live or latest value, which the template cannot hold; its `History` segment refers to the series in a time-series database. Not aas-model's Variables submodel ([state-and-parameters.md](state-and-parameters.md), Section 3) |
| How do AAS elements tie to the ontologies? (26 Oct) | Three ids, three jobs. The `semanticId` says what an element is in its submodel template; the ontology of that kind of AAS (ARSO, APSO, AProSO) names the class an element with that id belongs to, as ARSO does today. A `supplementalSemanticId` says what the element means in the domain: a class of the lab's vocabulary below CSS (a capability, a skill type, a property, a command, a state). Which individual an element is (this skill, this step) is its own id or reference, never a semantic id: the per-instance semantic ids written today (`.../skills/Dispensing/Execute/NeedleDown/Position`) are moved out, and `modlink`'s join of a data point to its variable changes with them |
| APSO and AProSO (26 Oct) | Remade like ARSO, from the submodels that are built: one class per template element with its semantic id, the restrictions, templates and classes generated from them, and checked like a resource AAS. Their versions of 30 Sep describe a Bill of Process and a process AAS that nothing builds |
| Templates for our own submodels (26 Oct) | Skills, Control Configuration, Operational Data, Production Sequence and the extension of Process Parameters each get a submodel template (the JSON) and a description of its elements as IDTA's specifications give them, both generated from the ontology. For our own use and the paper |
| How much of the product, process and resource model now? (26 Oct) | The whole model is designed now, as the overview the work proceeds by: every kind of AAS, its submodels and templates, the ontologies and the ids that join them. Built before the paper: the vocabulary of skill types, the projection of Skills and Capability Description into RDF, and capabilities derived from skills. The rest after the paper |
| Product, process and resource AAS (26 Oct) | As ISA-88's recipe levels. The **product AAS** is the general recipe: bill of material, processes with their parameters, required capabilities and the recipe (the Production Sequence without bindings). The **process AAS**, one per product and line, is the master recipe: the bindings of each step to a resource, a skill and its parameters, and the plan check's result. The **resource AAS** is as before. The process sequence planner takes the recipe from the product AAS, binds each step to a skill by capability matching or by hand, and writes the bindings into the process AAS. Order and product instance (the as-built record) come with the agents. Overview: [ppr-model.md](ppr-model.md) |
| How capabilities are derived (26 Oct, made while building F1 to F3; open to change) | A skill type (`ontology/Vocabulary/skills.ttl`) says which capability it contributes; capabilities are of two kinds, process (a product can require it) and auxiliary (Positioning, Weighing: they serve other skills and are never offered). What a parameter means is said on the primitive's parameter (the spec's `meaning`); a module level skill's parameter inherits it through its binding. Only module level skills offer capabilities. Derived elements carry the qualifier `Derived` (xs:boolean); a skill described but not built gives its capability `Availability = AfterReconfiguration`. The spec's `realized_by` and a property's `parameter` are gone: the spec states only the facts of the machine |
| Where does the Control Configuration go? (27 Oct) | Split ([control-configuration.md](control-configuration.md), option C). The AAS keeps the rule set the program follows (`RuleSet`) and, per module level skill, whether it is built or only described (`Deployment`), both in the Skills submodel; the instances with block types and hashes, the change log, the management endpoint and the provenance go into the integrator's backend (the registration service's record). ARSO changes with it |
| Branches, conditions and parallel steps in a skill (27 Oct) | Before the paper ([skill-authoring.md](skill-authoring.md), section 3): new library blocks, rule set 2, modgen, modsync, the editor with the planner's flow kinds. Installing the new FORTE on the Pis waits for your go at the bench |
| The skill editor (27 Oct) | An overview on the Skills submodel, the editor on a single skill; the planner's flow editor shared; the derivation called after saving; the planner shows `Availability`. The fork's pending changes (fixes, ARSO 0.9) committed first |
| How are new skills made? (27 Oct) | Planned by the module from its Capability Description: an HTN hybrid (compositions, existing composites and methods generated from the capabilities' postconditions, goal regression), lifted to parallel blocks, created online by `modsync`; HDDL and PDDL generated from the same model for standard planners. Only the module level is planned: the line is run by agents, and optimality is not a goal. Composites of composites are rare and inlined ([skill-planning.md](skill-planning.md)) |
| What the planner reads (27 Oct) | The module's own Capability Description (IDTA 02020 keeps its relations inside one submodel): its process capabilities (Offered) and a set per component with the component's capabilities (NotAssigned), realized by its primitives. A constraint is a `BasicConstraint` expression over the capability's properties; a property names the state it is with `SameProperty` (a data point of Operational Data). No planning submodels of their own, unlike AAS2PDDL (Nabizada et al.) |
| ARSO 0.11 (27 Oct) | A primitive's `Contract` becomes `Conditions` (Precondition, Postcondition, Invariant) and `Completion` (After, Timeout); `CapabilityRealizedBy` may name a component's skill; the constraint elements and conventions are declared. The module specs use the same words since 28 Oct (`precondition`, `postcondition`, `invariant`, `after`, `timeout`) |
| What the paper contributes (27 Oct) | The skill and capability models; planning new behaviour from them; the IEC 61499 module architecture that makes skills; updating a running module online through IEC 61499's management interface. Planning (G in [next-steps.md](next-steps.md)) is the next step |
| The framework's name and home (31 Oct) | AASPIRE: AAS-based Planning, Integration, Reconfiguration and Execution. One GitHub organization for the AP2030 project holds every repository, the lab's other AAS work included (planning with PDDL, behaviour trees, the DMP); its main repository is the framework, `aaspire` ([framework-plan.md](framework-plan.md)) |
