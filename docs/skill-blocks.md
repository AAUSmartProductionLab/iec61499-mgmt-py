# Filling-cell building blocks in 4diac

The 4diac project [`4diac/FillingCellFixed`](../4diac/FillingCellFixed) is generated by
[`generate_filling_cell.py`](../4diac/tools/generate_filling_cell.py). Do not edit the XML by
hand. Change the generator, then run [`validate.ps1`](../4diac/tools/validate.ps1) for the
headless IDE type/system check and C++ export, and
[`build-runtime.ps1`](../4diac/tools/build-runtime.ps1) to build FORTE through the 4diac FBE.

## Why this structure

| Question | Decision | Reason |
| --- | --- | --- |
| Basic, simple or composite? | **Primitive skill = composite** (`SK_*`) of standard blocks; logic in Basic/Simple FBs | One tested state machine for all skills; the only skill-specific code is the contract |
| When a SIFB? | Only where the runtime boundary is crossed: OPC UA (`SERVER`, `PUBLISH`), Modbus (`CLIENT`), GPIO (`IX`/`QX`/`IW` + `GPIOChip`), timers (`E_DELAY`, `E_CYCLE`) | FORTE ships all of these. A custom SIFB means hand-written C++; none is needed |
| OPC UA methods instead of state machines? | **No**: methods are the command transport, the PackML machine stays in the controller | FORTE blocks each method call until `RSP`, at most 4 s, one call at a time. A skill runs longer, so a method only accepts or rejects; completion is the subscribed `State` (OPC UA Programs / PackML OPC 30050 pattern). Guards, invariants and Hold/Stop/Abort must hold whoever calls |
| Where does IO live? | Actuators inside the skill that drives them; sensors once, in `UNIT_Observer` | A QX has one owner. Sensors are shared by several contracts and are the contract vocabulary (Operational data) |
| Central dispatcher? | **No**: a gate per skill plus a status chain through the `EM_Filler` subapplication | Skills can be added to or rewired in the equipment module online without changing a compiled type |

## Layers

```
FillingCell application (one FORTE resource)
├─ fixed: UaFacade (UNIT_Facade)  Unit (FC_Unit)  Occupation (FC_Occupation)  Facade (FC_ProcedureFacade)
│         Observer (UNIT_Observer: IO_DI/IO_AI -> FC_Observer -> Cell struct, published state variables)
├─ EM_Filler subapp: MoveDown -> Dose -> MoveUp -> Stopper -> Inspect   (SK_* composites, status chain)
└─ PROC subapp: empty; the generated procedure calls skills through CALL_x / DONE_x / FAILED_x
PiIoConfig application: GPIOChip line configuration (map on the Pi resource only)
```

Inside every `SK_*` composite:

| Instance | Type | Role |
| --- | --- | --- |
| `Gate` | `SKILL_Gate` (BasicFB) | Authority. Procedure `CALL` only while the unit runs, one at a time, with a reset-then-start handshake. OPC UA commands only from the occupation owner, outside Production, in a valid state; Start also needs a quiescent unit. Unit control is always forwarded. Answers each OPC UA command synchronously |
| `Pml` | `SKILL_PackML` (BasicFB) | Reduced PackML machine shared by all skills. Start only if `RequiresOK`; Complete only on `EnsuresOK`; Abort on invariant violation or watchdog |
| `Logic` | `SL_<Skill>` (SimpleFB) | The contract: `CHECK` → RequiresOK, `LATCH` → latched P1..P4 (Dose: target volume), `EVAL` → EnsuresOK, InvariantOK |
| `Wd` | `E_DELAY` | Watchdog while in Execute (`Timeout` parameter) |
| `Chain` | `SKILL_Chain` (SimpleFB) | Busy/Held/Running aggregation along the equipment module |
| `Ua` | `UA_SkillFacade` (composite) | One `SERVER` per PackML command, a mux (`UA_SkillMux`), `PUBLISH` of State, ErrorID, P1..P4 |
| `Out` | `IO_DO` (composite) | The skill's actuator; `Drive = Active` (Execute only) |

`IO_DO`, `IO_DI` and `IO_AI` contain both a GPIO SIFB and a Modbus `CLIENT`. `IoBackend`
selects which one is initialised: 0 simulated (`Sim*` inputs), 1 GPIO, 2 Modbus. The type
hash is therefore identical on the simulator and on the Pi.

## Uniform skill interface

| Direction | Event | Data |
| --- | --- | --- |
| in | `INIT` | `UaRoot`, `UaEnable`, `IoBackend`, `DoGpio`, `DoModbus`, `Timeout` (parameters) |
| in | `CALL` | `P1..P4 : LREAL` (procedure call port; one caller per skill) |
| out | `DONE`, `FAILED` | `CallError` |
| in | `UNIT_CTL` | `ControlCode` (unit Reset/Hold/Unhold/Stop/Abort/Clear) |
| in | `UNIT_STAT` | `UnitRunning`, `UnitQuiescent`, `UnitState`, `Mode`, `Owner`, `RemoteAllowed` |
| in | `SAMPLE` | `Cell : ST_CellState` |
| in/out | `STAT_IN` / `STAT_OUT` | `BusyIn/HeldIn/RunIn` → `BusyOut/HeldOut/RunOut`, `State`, `SkillError`, `Drive` |

Codes: PackML states as in ISA-TR88 (Idle 4, Execute 6, Complete 17, Held 11, Stopped 2,
Aborted 9, …); commands Reset 1, Start 2, Hold 3, Unhold 4, Stop 5, Abort 6, Clear 7,
Suspend 8, Unsuspend 9; errors 1 PreconditionViolated, 2 InvariantViolated, 3 Timeout,
4 NotReady (invalid in this state), 5 NotPermitted (occupation/mode), 6 Busy, 7 Interrupted.

## OPC UA address space (AID properties and actions)

Below `/Objects/FillingCell/Filler` (namespace 1):

| Node | Kind | Arguments → result |
| --- | --- | --- |
| `Occupation/{Occupy,Release,Local,Prioritize,Remote}` | method | `Requester:UInt32` → `Accepted:Boolean, ErrorID:UInt16` |
| `Unit/Reset` | method | `Requester, Mode:Byte` (0 Production, 1 Maintenance, 2 Manual) → idem |
| `Unit/{Start,Hold,Unhold,Stop,Abort,Clear,Suspend,Unsuspend}` | method | `Requester` → idem |
| `Unit/State`, `Unit/Mode`, `Occupation/State`, `Occupation/Owner` | variable | published on change |
| `Skills/<Skill>/Start` | method | `Requester, P1..P4:Double` → idem |
| `Skills/<Skill>/{Reset,Hold,Unhold,Stop,Abort,Clear}` | method | `Requester` → idem |
| `Skills/<Skill>/{State,ErrorID,P1..P4}` | variable | published on change / latch |
| `State/{NeedleUp,…,DoorClosed,Valid,Safe}` | variable | published every sample |

`Accepted` means the command was authorised, valid in the current state and delivered.
For a skill Start it means the skill left Idle, i.e. its Requires held. The outcome
is observed on `State`. Unit Start is only possible in Production mode and is the procedure
(composite skill) start; skill methods are for Maintenance/Manual mode.

## Changing the equipment module online

A skill added while the unit is quiescent needs the following steps (exercised by
`test_equipment_module_changed_online`):

1. `CREATE` the composite as `EM_Filler.<Name>`, `WRITE` its parameters.
2. Connect the fan-out inputs (`UNIT_CTL`, `UNIT_STAT`, `SAMPLE` and their data).
3. Splice the chain: the previous last skill's `STAT_OUT`/`*Out` now go to the new skill; the
   new skill's go to `Unit.STATUS`/`Busy`/`HeldAll`/`RunAll`.
4. `START` the instance and fire its `INIT`. This creates its OPC UA object.

Removal is the reverse. The fixed part is never stopped. New skill *types* still require a
FORTE build, as they are compiled and pinned by type hash.

## Procedure patterns (`PROC`)

Each BPMN element becomes one pattern instance in `PROC`. Counts, conditions and durations are
parameters, so a product change that only alters them is a WRITE.

| Type | Events | Parameters | Behaviour |
| --- | --- | --- | --- |
| `P_Call` | `EI` → `CALL`; skill `DONE`/`FAILED` → `EO`/`ERR`; `RESET` | `P1..P4` (out `CP1..CP4` to the skill) | Calls one skill; ignores completions it did not request |
| `P_Loop` | `EI`, `NEXT` → `BODY`, `EO`; `RESET` | `Count : UINT` | Runs the body `Count` times; 0 skips it |
| `P_Choice` | `EI` → `EO_TRUE` / `EO_FALSE` | `Cond : BOOL` | Exclusive gateway; the merge is event fan-in |
| `P_Fork` | `EI` → `EO1..EO4` | none | Parallel split |
| `P_Join` | `EI1..EI4` → `EO`; `RESET` | `N : USINT` | Fires once `N` branches have arrived |
| `P_Wait` | `EI` → `EO`; `RESET` cancels | `DT : TIME` | Timer event |

The procedure facade gives `PROC` a `START` (unit Execute) and a `RESET` (unit Resetting).
The last pattern's `EO` goes to `Facade.FINISHED` and every `ERR` to `Facade.FAILED`. The unit
completes on `FINISHED`. A failure while the procedure is active aborts the unit; a call
interrupted by a unit Stop does not. Each skill has one data writer per input, so the translator
gives every skill one `P_Call` and repeats it with `P_Loop`.

## Deployment tools in `iec61499_mgmt`

| Module | Use |
| --- | --- |
| `typelib` | `read_types` (interfaces from the .fbt files) + `query_hashes` (live `QUERY FBType`) → `build_library` (types.json with boundary ports of the fixed application). CLI: `python -m iec61499_mgmt types` |
| `bootfile` | `deployment` (resource, fixed application, procedure, start) → `boot_file` (FORTE `.fboot` lines). CLI: `python -m iec61499_mgmt boot` |
| `verify` | `verify(client, network)` compares instances, types, running state, connections and parameter values in `PROC` with the expected network |

```powershell
python -m iec61499_mgmt types --types-dir "4diac/FillingCellFixed/Type Library" --prefix fillingcell:: --system 4diac/FillingCellFixed/FillingCellFixed.sys --port 61499 --out types.json
python -m iec61499_mgmt boot --system 4diac/FillingCellFixed/FillingCellFixed.sys --procedure network.json --library types.json --out forte.fboot
```

## Running from the 4diac IDE

Custom types (basic, simple and composite) must be compiled into the runtime, so the IDE's
bundled FORTE cannot run them. Use the FBE build, which contains all generated types.
`build-runtime.ps1` rebuilds it whenever the generator adds or changes a type.

1. Import `4diac/FillingCellFixed` (File → Import → Existing Projects into Workspace).
2. Start the runtime with `4diac/tools/fbe/build/fillingcell-win/output/bin/forte.exe -c localhost:61499`,
   or point Window → Preferences → 4diac IDE → FORTE location to it and use "Launch local FORTE".
3. In the System Configuration, device `FORTE_PC` (`localhost:61499`) has one resource per
   application. Right-click the device → Deploy, then switch to monitoring and watch or force values.

| Resource | Application | What to do |
| --- | --- | --- |
| `RES` | `FillingCell` (production) | Waits in Stopped for OPC UA commands at `opc.tcp://localhost:4840` (UaExpert: `Objects/FillingCell/Filler`). Simulated IO: force `Observer.Sim_*`. For Modbus, set every `IoBackend` to 2 and run `python 4diac/tools/cell_sim.py` |
| `DEMO` | `FillingCellDemo` | Runs by itself: `DEMO_Operator` occupies, resets in Production, starts, waits for Complete, swaps the vial and repeats; `DEMO_Plant` simulates the cell. Watch `Operator.Cycles`/`Phase`, `Unit.State`, `Plant.FilledMl`, `EM_Filler.<Skill>.State`. Set `Operator.Enable` FALSE to stop after the current vial; trigger `Operator.START` to restart |
| `BENCH` | `SkillBench` | One `SK_Dose` called every 2 s with 0.3 mL against the plant model; `Done.CV` and `Failed.CV` count the results |
| `PATTERNS` | `PatternDemo` | Fork/wait/join, a 3-iteration loop and an alternating choice every 3 s; watch the `Ctu*` counters |

`PiIoConfig` is not mapped; put it on a Raspberry Pi device together with `FillingCell`
(`IoBackend = 1`). FORTE 3.3 (like 3.2) serves OPC UA for only one resource per process: whichever
initialises it first gets the server. Only `FillingCell` enables OPC UA, so the demo resources
are watched through IDE monitoring. `tests/test_ide_apps_live.py` loads all four resources into
one FORTE, as a full deployment would, and checks that each one runs.

## Build and test

```powershell
python 4diac/tools/generate_filling_cell.py
4diac/tools/validate.ps1                    # IDE check + export (4diac IDE 3.3)
4diac/tools/build-runtime.ps1 -SkipValidate # FBE: open62541, libmodbus, FORTE + our types
python -m pytest tests/test_skill_blocks_live.py -q --forte-exe 4diac/tools/fbe/build/fillingcell-win/output/bin/forte.exe
python 4diac/tools/cell_sim.py              # Modbus simulator for IoBackend 2 (port 1502)
```

The Raspberry Pi build is `build-runtime.ps1 -Config configurations/pi` (aarch64-linux-musl
cross compiler, downloaded once). Deploy `FillingCell` with `IoBackend = 1` together with
`PiIoConfig` on the same resource. The BCM line numbers in the generator are an example
wiring.

## Verified on FORTE 3.3.0 (Windows build via FBE, 27 Sep 2026)

The types are exported by 4diac IDE 3.3 and compiled with FORTE 3.3.0, fetched and pinned by
`build-runtime.ps1 -ForteTag 3.3.0` into `4diac/tools/fbe/4diac-forte`. The IDE export and the
runtime must come from the same release, because FORTE refuses a CREATE whose type hash differs.

`tests/test_skill_blocks_live.py` and `tests/test_procedure_live.py` run against the FBE
build (`--forte-exe`), together with `tests/test_changeover_live.py`. Three consecutive runs of
the whole suite passed (76 tests). The live
tests cover:

- **Types**: every exported type is present in the runtime with a type hash.
- **SKILL_PackML**: the full transition table, including the Requires guard, completion
  by Ensures, invariant and watchdog aborts, and commands ignored where invalid.
- **SKILL_Gate**: the authority matrix (owner, mode, state validity, quiescence, one
  pending start or call).
- **`SK_Dose` with simulated IO**: range rejection, latching, completion, reset-then-start
  on a repeated call, invariant abort with `CallError`, unit Clear/Reset, and the watchdog.
- **Whole cell over OPC UA**: occupation, Reset in Maintenance mode, manual skill Starts
  answered synchronously with `[Accepted, ErrorID]`, completion from sensor feedback, the
  unit refusing Start outside Production, abort when the door opens, then Clear and Release.
- **Online equipment-module change**: a second `SK_Inspect` created, chained, started and
  commanded while every other instance kept `RUNNING`.
- **Modbus backend** against `cell_sim.py`: MoveDown → Dose 0.4 mL → MoveUp → Stopper →
  Inspect completes from simulated physics, with the coil order checked and no
  shoot-through.
- **Type library from the runtime**: every filling-cell type queried with a `v2:SHA3-512` hash.
  CREATE with a wrong hash is refused (`UNSUPPORTED_TYPE`), so pinning holds end to end.
- **Procedure in Production mode** (Modbus simulator): `P_Call` MoveDown → Dose 0.3 mL →
  MoveUp runs to unit Complete. Online, it changes to a `P_Loop` around Dose (structural,
  verified by read-back) and runs again, filling twice. Then the loop count changes by one
  WRITE. The fixed part stays `RUNNING` throughout, with no shoot-through.
- **Boot file**: the fixed application plus `PROC` restored on a fresh runtime, verified by
  read-back and commanded over OPC UA.
- **Pattern FBs**: choice, fork/join, wait (including cancel) and loop (including zero
  iterations).
- **Product changeovers** (`tests/test_changeover_live.py`): the cell BPMN versions are
  compiled against the runtime's types, contract-checked and applied with `changeover()`.
  Deploying A (0.5 mL) is structural. A → B (1.0 mL) is one WRITE, and B → C (two cycles) is
  one WRITE of the loop count. C → D (v3 with inspection) is structural. Each run fills the
  expected volume from simulated physics. An occupied unit and runtime drift are rejected,
  and product E (3.0 mL) fails the range check.

The GPIO backend and the Raspberry Pi build are configured but not yet run on hardware.

### Runtime findings and the workarounds in this repository

| Finding | Workaround |
| --- | --- |
| Deadlock: open62541 1.5 defaults to `UA_MULTITHREADING=100`. During a method call the server thread holds open62541's lock while FORTE waits for `RSP`. A `PUBLISH` in the same event chain takes FORTE's `mServerAccessMutex` and then blocks on that lock | `UA_MULTITHREADING:STRING=0` in the FBE configs (FORTE's own mutex serialises server access) |
| libmodbus 3.1.12 rejects sockets `>= FD_SETSIZE` (EINVAL "Invalid argument"). On Windows socket handles are arbitrary values and mingw's `FD_SETSIZE` is 64 | Recipe override `fbe/dependencies/recipes/libmodbus` compiles libmodbus with `FD_SETSIZE=4096` |
| The IDE 3.3 exporter (like 3.2) includes `forte/eclipse4diac/io/IX_fbt.h` (process-interface variant); modular IO (`FORTE_IO`, gpiochip) provides `forte::io::FORTE_IX` in `forte/io/` | Alias headers in `4diac/tools/forte-compat`, copied into the export |
| The exported module links only `forte-core` | `validate.ps1` appends links to `forte-events` and `forte-net` |
| An FB receiving an event reads the source's *current* output: `Starting` passes to `Execute` in one ECC run, so a listener never sees State 3 | The gate acknowledges a start on "left Idle", not on "State = 3" |

The headless IDE does not resolve library dependencies. The generator therefore copies
the interface declarations of the standard types it uses from
[`4diac/tools/stdtypes`](../4diac/tools/stdtypes) into `Type Library/Std`, and
`validate.ps1` removes them, plus the generic `SERVER_x_y` declarations, from the export.
